Data handling

How this prototype handles data

A system built to hold health records should be able to say exactly what it does with them. This page is that statement for the prototype as it stands today, and for the system it is being built into.

This is a prototype, and there is no database yet

What you are looking at is the frontend of a Database Management System course project. There is no server and no database behind it. Every hospital, doctor and patient you can see is invented sample data written into the JavaScript files. No information about any real person is present anywhere in it.

What is stored, and where

Anything you do in the prototype is written to your own browser’s local storage and stays on the device you are using. Specifically:

  • patients registered through the registration screen;
  • ward bed state, so an admission survives moving between screens;
  • which demo role you signed in as.

None of it is transmitted anywhere, because there is nowhere for it to go. Clearing your browser data removes all of it, and so does Reset demo data on the sign-in page.

What leaves your browser

One thing: the IBM Plex typefaces are requested from Google Fonts, so Google receives the request for those font files as it would on any site that loads them. There is no analytics, no tracking, no advertising, and no cookies of any kind.

The demo passwords are not security

The four demo accounts and their shared password sit in client-side JavaScript that anyone can read. That is a stand-in for a sign-in screen, and nothing more. In the finished system accounts live in a user_account table, the password is stored as a bcrypt hash, and the check happens on the server where the browser cannot reach it.

What the real system will do

The rules below are the point of the project rather than an afterthought to it, and they are enforced by the database rather than by application code that could forget to run:

  • Consent with an expiry. A hospital is granted access to a record for a period, by the patient, and the grant lapses on its own.
  • An access log written by a trigger. Every clinical read is recorded — who, where, when, and on what basis — by the database itself, so it cannot be bypassed by a code path that neglects to write it.
  • Break-glass access, flagged. Emergency staff can open a record without prior consent, because a patient arriving unconscious cannot give one. That read is allowed, recorded, and marked for review afterwards.
  • Role-based permission. Reception sees the demographics needed to register someone. It does not see their diagnoses.
