Data handling

How this prototype handles data

A system built to hold health records should be able to say exactly what it does with them. This page is that statement for the prototype as it stands today, and for the system it is being built into.

This is a course project, and every record in it is invented

What you are looking at is a Database Management System course project. Every hospital, doctor and patient in it is invented sample data. No information about any real person is present anywhere in it. It can run in two ways, and what happens to data depends on which.

Run with its server: the data lives in a MySQL database

Started with its Express server, the site keeps everything in a MySQL database on the computer running that server — registrations, appointments, admissions, and the log of who opened which record. Nothing is sent to any other machine. Signing in sets one cookie, holding a random session number and nothing else, so the server knows it is still you; it is deleted when you sign out, and the session ends by itself after 30 minutes without activity or 8 hours after signing in.

The browser never holds a list of patients. Staff find someone by searching for that one person; at most twenty come back, with the national ID and mobile number masked, and each person shown is written to the access log.

The browser keeps a few small things for convenience, none of them clinical:

  • in local storage, which role you signed in as (uhid.session.v1), so the menu can be drawn before the server answers — the server still decides who you are;
  • in session storage, for the open tab only and gone when it closes: the UHID and name of the patient you last opened (to label the screens), a search you started from the top bar on its way to the search screen, and the text of a message waiting to be shown on the next page (which can include a patient’s name).

Opened straight from disk: the data stays in your browser

Opened as files, with no server, the pages use built-in sample data, and anything you do is written to your own browser’s local storage on the device you are using:

  • patients registered through the registration screen;
  • ward bed state, so an admission survives moving between screens;
  • which demo role you signed in as.

None of it is transmitted anywhere. Clearing your browser data removes all of it, and so does Reset demo data on the sign-in page.

What leaves your browser

Apart from requests to the project’s own server when one is running: the IBM Plex typefaces are requested from Google Fonts, so Google receives the request for those font files as it would on any site that loads them. There is no analytics, no tracking, and no advertising.

Sessions and server logs

When you sign in, your browser keeps one cookie holding a random session id. The server keeps the session in its database, under a one-way hash of that id, so that a restart does not sign you out; it ends after 30 minutes without use, or 8 hours after sign-in. Switching an account off or resetting its password ends its sessions at once. The server also writes one line per request to its own log file — the time, the address asked for, the answer, how long it took and an account number — with patient UHIDs masked and no form contents. Who opened which record is kept separately, in the access log every patient can read.

Passwords

With the server, accounts live in a user_account table, each password is stored only as a bcrypt hash, and the check happens on the server where the browser cannot reach it. A new account, or a reset, gets a one-time password that is shown once to the administrator or receptionist who made it and must be replaced at the first sign-in; nobody, administrators included, can read a password back. The demo accounts and their shared password are listed only on a demonstration installation. Opened from disk there is no server, so the four demo accounts are checked in JavaScript that anyone can read — a stand-in for offline demonstration, and nothing more.

The rules the database enforces

These are the point of the project rather than an afterthought to it, and they are enforced by the database rather than by application code that could forget to run:

  • Consent with an expiry. A hospital is granted access to a record by the patient, or by a referral, for 24 hours, and the grant lapses on its own.
  • Every read is logged first. A clinical record can only be opened through a stored procedure that writes who, where, when and on what basis to an append-only access log before it returns anything. The web server’s own database account cannot read the record tables any other way, and cannot edit or delete the log.
  • Break-glass access, flagged. A clinician can open a record without prior consent in an emergency, because a patient arriving unconscious cannot give one. That read needs a written reason, is recorded, and waits for review by the hospital administrator.
  • Role-based permission. Reception sees the demographics needed to register someone. It does not see their diagnoses.
  • Scope as well as role. Being a doctor is not enough to read a record: the doctor needs their own encounter, a consent or an emergency reason. Ward actions, cancellations and record merges are limited to the staff member’s own hospital.
